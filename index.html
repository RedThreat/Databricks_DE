1 · Databricks Intelligence Platform 6%

Pouco peso, mas perguntas rápidas: arquitetura, Delta e escolha de compute.

  • Control plane fica sempre na conta Databricks. Compute plane: serverless (conta Databricks) ou clássico (a tua conta cloud).
  • Lakehouse = object storage com formatos abertos + transações ACID (Delta) + governança única (Unity Catalog).
  • 1 metastore UC por região, ligado a vários workspaces; os grants valem em todos.
  • No clássico pagas DBU + VM; no serverless o DBU já inclui a VM.

Do Notion: o que acrescenta a este resumo
  • Time travel e RESTORE precisam da retenção do log (30 dias) e dos ficheiros (VACUUM, 7 dias). RESTORE fica registado como versão nova.
  • Schema evolution por operação (MERGE WITH SCHEMA EVOLUTION, mergeSchema); autoMerge de sessão é legacy.
  • Stream sem trigger falha em serverless (INFINITE_STREAMING_TRIGGER_NOT_SUPPORTED): usa availableNow.
  • SQL warehouses só correm SQL; serverless SQL warehouse arranca em segundos (pro/classic ~4 min) e auto stop por defeito aos 10 min.
  • Serverless jobs: performance optimized desligado = modo standard (arranca em 4–6 min, gasta menos DBUs).
  • Standard access mode não suporta R: R + RDD → classic job compute em dedicated.

Do Notion: o que acrescenta a este resumo
  • COPY INTO: FILES (até 1000) e PATTERN não se combinam. FORMAT_OPTIONS mergeSchema = schema da fonte; COPY_OPTIONS mergeSchema = evolui o destino. Ficheiro corrigido: apaga as linhas antigas e só depois faz FILES + force. VALIDATE testa sem escrever.
  • Auto Loader: inferência sobre os primeiros 50 GB ou 1000 ficheiros. Com addNewColumns o stream falha e evolui ao reiniciar → job com retries + mergeSchema na escrita. Com schema fornecido, o _rescued_data só existe se definires rescuedDataColumn.
  • read_files infere tipos; Auto Loader infere strings (JSON/CSV/XML).
  • singleVariantColumn: registo inteiro em VARIANT, sem schema evolution nem rescued data. [*] só em JSON string; em VARIANT usa variant_explode. Campos de VARIANT são case sensitive.
  • Upload pela UI: até 10 ficheiros, menos de 2 GB no total, sem comprimidos. Maior → volume (até 5 GB por ficheiro na UI).
  • Managed connectors: CDC de bases de dados usa um gateway contínuo (não o pares); CREATE CONNECTION / USE CONNECTION; SCD1 por defeito, SCD2 onde suportado; apagar a pipeline apaga as tabelas.
  • JDBC: lowerBound/upperBound não filtram. REST: segredos, paginação, backoff em 429, escrever em volume.
  • Audit logs entregues podem ser reescritos → cloudFiles.allowOverwrites=true + dedup; ou lê system.access.audit (365 dias).
  • Ordem de escolha: managed connector → Lakeflow pipeline → Structured Streaming. Tabelas criadas pelo Partner Connect pertencem ao service principal do parceiro.

PySpark e SQL que costumam apanhar

  • x = NULL nunca é verdadeiro: usa IS NULL, isNull(), coalesce. Chaves NULL não fazem join; <=> / eqNullSafe fazem.
  • fillna(0) só preenche colunas numéricas; para várias: fillna({"q": 0, "r": "n/a"}).
  • Com ANSI ligado, um CAST inválido falha: usa try_cast. Em to_date(s,'dd/MM/yyyy'), M é mês e m é minuto.
  • join(o, "k") deixa uma cópia da chave; join(o, a.k == b.k) deixa duas (risco de AMBIGUOUS_REFERENCE).
  • left_semi / left_anti: existe / não existe correspondência.
  • union em PySpark = UNION ALL por posição; UNION em SQL remove duplicados; unionByName(allowMissingColumns=True) junta por nome.
  • split devolve array; [i] começa em 0, element_at em 1. explode descarta arrays NULL ou vazios; explode_outer mantém.
  • dropDuplicates(["k"]) fica com uma linha qualquer. Para a mais recente: row_number() numa janela ordenada por ts desc (SQL: QUALIFY).
  • count(*) conta tudo; count(col), avg, sum ignoram NULL. approx_count_distinct é aproximado.
from pyspark.sql import functions as F, Window
w = Window.partitionBy("customer_id").orderBy(F.col("updated_at").desc())
latest = df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")

-- SQL
SELECT * FROM orders
QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) = 1;

Do Notion: o que acrescenta a este resumo
  • ANSI ligado por defeito (DBR 17.0+): CAST inválido falha (CAST_INVALID_INPUT) → try_cast. to_date sem formato espera yyyy-MM-dd.
  • split(x,'-')[2] fora do limite falha (INVALID_ARRAY_INDEX) → try_element_at(…, 3), base 1.
  • MERGE com duplicados na fonte → DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE.
  • mode("overwrite") mantém o schema (precisa de overwriteSchema); CREATE OR REPLACE mantém histórico, grants, row filters e masks.
  • RENAME/DROP COLUMN precisam de column mapping; DROP COLUMN não apaga os dados (REORG … APPLY (PURGE) + VACUUM). withColumnRenamed e drop ignoram colunas inexistentes sem erro.
  • Sem ON em SQL = cross join. Broadcast só do lado pequeno (o hint ignora o threshold).
  • row_number precisa de desempate único; count(DISTINCT col) também ignora NULL; approx_count_distinct rsd 0,05.
  • Tuning: AQE tem threshold de broadcast em runtime de 30 MB; spark.default.parallelism só afeta RDD; spark.driver.memory não muda em runtime; serverless só aceita poucas Spark confs.
  • MV/ST standalone precisam de SQL warehouse pro ou serverless; o refresh corre como o dono. Mudar a query de uma ST só afeta linhas novas.
  • Expectations: FAIL faz rollback e não regista métricas; só Python agrupa (@dp.expect_all…). CHECK constraint aplica-se a todos os writers. Quarentena para guardar rejeitados.

4 · Working with Lakeflow Jobs 16%

As perguntas pedem a configuração certa: dependências, condições, retries e triggers.

  • Tipos de task: notebook, SQL, dashboard, pipeline, Python script/wheel, Run Job, If/else, For each.
  • DAG com depends_on; o que não tem dependências corre em paralelo. job_cluster_key partilha um cluster entre tasks.
  • Parâmetros do job sobrepõem-se aos da task com a mesma chave.
  • Passar valores: dbutils.jobs.taskValues.set(key, value) / .get(taskKey, key), ou {{tasks.ingest.values.row_count}}.
  • Retries por task: max_retries (0 por defeito), min_retry_interval_millis, retry_on_timeout. timeout_seconds mata a tentativa; um warning só notifica.
  • Repair run: volta a correr só as tasks que falharam e as dependentes.

Do Notion: o que acrescenta a este resumo
  • If/else: == e != comparam strings; < > <= >= comparam números. Run if não cumprido → task Excluded.
  • For each: input de JSON array, task value, job parameter ou SQL; {{input}}; concorrência 1–100.
  • Timeout é por tentativa (30 min × 3 retries ≈ 2 h). Serverless pode fazer retries por conta própria.
  • Job até 1000 tasks. SQL task em warehouse serverless ou pro (não classic). Notebook num warehouse só se for todo SQL.
  • Job com pipeline task: máximo 1 run concorrente. Serverless script/wheel/dbt tasks precisam de environment_key. Shared job cluster não declara libraries.

  • Git folders: branch, commit & push, pull, merge, rebase na UI. O pull request é no fornecedor Git. Um Git folder por pessoa.

Do Notion: o que acrescenta a este resumo
  • Segredos: variável sem default + BUNDLE_VAR_x no CI; em runtime, secret scope. Nunca no default nem no target (vão para o Git).
  • Targets fazem merge com a definição de topo (tasks e job clusters por key): só pões o que muda.
  • bundle run --var não muda nada → usa --params. Caminhos relativos ao ficheiro YAML onde estão (../src/…).
  • Production mode valida o branch (git.branch) e o run identity; --force contorna (não usar). Development mode: prefixo, tag dev, triggers pausados, runs concorrentes.
  • Remover um recurso do YAML apaga-o no próximo deploy (lifecycle.prevent_destroy). Jobs do bundle são read-only na UI (Disconnect from source em emergência). Não fazer deploy de produção para /Shared.
  • CLI: --auto-approve em CI; --force-lock só para lock órfão; --select não é para produção; bundle summary. Comandos atuais: databricks jobs cancel-run|get-run|repair-run <id>. Bundles precisam da CLI ≥ 0.218.
  • CI: service principal com workload identity federation (DATABRICKS_AUTH_TYPE=github-oidc) ou OAuth M2M.
  • Git folders: branch/pull/push precisam de CAN MANAGE; mudar de branch apaga assets que não existem no branch alvo; Rebase e Reset fazem force push. Em produção, tasks com source = repositório Git remoto.

Do Notion: o que acrescenta a este resumo
  • Estado final vem das tasks folha: Succeeded with failures = só falharam tasks não-folha. Skipped = limite de runs concorrentes com queueing desligado (com queueing espera até 48 h).
  • Repair run só em jobs com 2+ tasks; recomeça a task do início → appends duplicam.
  • Warning (health rule RUN_DURATION_SECONDS) só notifica; Timeout termina como Timed Out.
  • Duration do run: Queued / Waiting for resources / Library installation / Running. Histórico na UI: 60 dias; system tables: 365.
  • Skew: Max ≥ 50% acima do p75. AQE só trata skew em sort merge/shuffle hash joins e partições > 5× mediana e > 256 MB. Agregações → salting.
  • Liquid clustering é incompatível com partitioning e ZORDER; PO corre em serverless, nunca faz ZORDER, ligado por defeito para contas criadas a partir de 11 nov 2024; histórico em system.storage.predictive_optimization_operations_history.
  • Falhas de arranque: event log → termination code → .stderr.log em <log-path>/<cluster-id>/init_scripts. Bibliotecas com versão fixa (==).

Do Notion: o que acrescenta a este resumo
  • UNDROP recupera tabelas managed e external (7 dias); não recupera schemas, catálogos, volumes, views nem funções. DROP SCHEMA é RESTRICT por defeito.
  • Ver o tipo: DESCRIBE TABLE EXTENDED (não DESCRIBE DETAIL). SET MANAGED reverte-se com UNSET MANAGED até 14 dias.
  • Só o dono do catálogo/schema (ou quem tem MANAGE) concede USE CATALOG / USE SCHEMA. MANAGE não dá acesso a dados. Privilégios de metastore não herdam.
  • Row filter: UDF BOOLEAN, 1 por tabela; column mask: 1 por coluna, extra inputs com USING COLUMNS. Aplicar: EXECUTE + dono da tabela. Ler em dedicated: DBR 15.4+ com serverless.
  • is_account_group_member (grupos de conta) vs is_member (workspace); current_user() deprecated → session_user(). Não se põe mask em views → dynamic view.
  • ABAC: tags de coluna não herdam; ASSIGN na tag + APPLY TAG no objeto; só 1 filtro/máscara por utilizador e tabela (conflito bloqueia); pipelines avaliam como o run-as → service principal no EXCEPT; SHOW EFFECTIVE POLICIES.

Armadilhas frequentes

  • DENY não existe no Unity Catalog.
  • REVOKE não tira acesso herdado.
  • DROP numa tabela external mantém os ficheiros.
  • VACUUM corta o time travel.
  • rescue não evolui o schema; addNewColumns falha primeiro e evolui ao reiniciar.
  • PySpark union não remove duplicados; SQL UNION remove.
  • Mais workers não resolvem skew nem OOM no driver.
  • Variáveis dos bundles resolvem-se no deploy, não no run.
  • Material antigo: DLT, Workflows, Repos e Asset Bundles são os mesmos temas com nomes novos. Não descartes uma opção só pelo nome.

Lab 1 · Delta Lake (dias 24–25 nov)

CREATE OR REPLACE TABLE sales (id INT, amount DOUBLE, region STRING);
INSERT INTO sales VALUES (1, 10, 'EU'), (2, 20, 'US');
INSERT OVERWRITE sales VALUES (1, 15, 'EU');           -- substitui
DESCRIBE HISTORY sales;                                  -- vê as versões
SELECT * FROM sales VERSION AS OF 1;                     -- time travel
RESTORE TABLE sales TO VERSION AS OF 1;
ALTER TABLE sales CLUSTER BY (region);                   -- liquid clustering
OPTIMIZE sales;
DESCRIBE DETAIL sales;                                   -- numFiles, clusteringColumns

Desafio: tenta INSERT OVERWRITE com uma coluna a mais. Falha? E com CREATE OR REPLACE TABLE ... AS SELECT? Vê o DESCRIBE HISTORY depois.

Lab 3 · PySpark e SQL (28 nov)

from pyspark.sql import functions as F, Window
a = spark.createDataFrame([(1,"Ana",None),(2,"Rui",["x","y"]),(3,"Eva",[])], "id INT, name STRING, tags ARRAY<STRING>")
b = spark.createDataFrame([("Ana",1)], "name STRING, id INT")

a.select("id","name").union(b).show()           # mistura colunas!
a.select("id","name").unionByName(b).show()     # correto
a.select("id", F.explode("tags")).show()        # perde ids 1 e 3
a.select("id", F.explode_outer("tags")).show()  # mantém
a.join(b, "id", "left_anti").show()             # sem correspondência
a.fillna(0).show()                              # tags/name não mudam
spark.sql("SELECT try_cast('abc' AS INT), element_at(split('a b',' '),1), split('a b',' ')[0]").show()

Lab 4 · Pipeline declarativa (29 nov)

Cria uma ETL pipeline (Jobs & Pipelines → ETL pipeline) com este ficheiro SQL:

CREATE OR REFRESH STREAMING TABLE orders_bronze
AS SELECT * FROM STREAM read_files('/Volumes/workspace/prep/raw/orders', format => 'json');

CREATE OR REFRESH STREAMING TABLE orders_silver (
  CONSTRAINT positive EXPECT (amount > 0) ON VIOLATION DROP ROW
) AS SELECT order_id, amount, customer.city AS city FROM STREAM(orders_bronze);

CREATE OR REFRESH MATERIALIZED VIEW sales_by_city
AS SELECT city, sum(amount) AS total FROM orders_silver GROUP BY city;

Desafio: vê no event log quantas linhas foram descartadas. Muda para sem ON VIOLATION e compara.
